1. Executive Summary

The app is further along than a typical MVP: onboarding, profiles, discovery, filters, bilingual UI and the whole Supabase data layer are built and verified working end to end. What is not finished is the part the roadmap calls the core loop — two people actually matching and talking to each other — plus the commercial and compliance work needed to hand the build to a client and put it in the stores.

The one thing that blocks everything else

Matching and messaging are currently single-sided. A match row and every chat message are written only under the sender's own profile_id; the other person never receives them. The "Move to Rishta" acceptance is a 2.2-second setTimeout simulation, and this is stated plainly in the code itself (src/store/MatchesContext.tsx: "There's no live backend/second user in this app"). Until this is rebuilt, the roadmap's central hypothesis — that Pakistani users will move a conversation from Dating to Rishta — cannot be measured at all. Days 1–5 of this plan exist to fix exactly that.

What is genuinely finished and verified

  • Backend, verified live against the production Supabase project. All 14 tables plus both storage buckets were written to and read back with a throwaway account: every one of the 54 profiles columns round-trips, media uploads return a public URL that renders without auth, CNIC/selfie files are reachable only through a signed URL, and a second signed-in member sees the first member's card with photos while being correctly blocked from their private tables.
  • Onboarding — 3-step flow, 2–4 photos enforced, selfie and CNIC both mandatory.
  • Bilingual UI — 541 keys in English, Urdu and Roman Urdu with RTL support; 6 Urdu strings still fall back to English.
  • Discovery — swipe deck, vibe tags, and manual filters covering age, city, intent, sect, readiness, verified-only and active-today, with ten sort modes.
  • Rishta profile — religion, sect, family background, education, readiness signal.
  • Free-tier like limit — 15/day, persisted per user per date.

Fixed during this audit (already in the branch)

  • Signup "Network request failed". Uploads used fetch('file://…'), which React Native cannot do. Media now reads through expo-file-system and uploads raw bytes.
  • Stranded accounts. Signup now writes profile rows before media, treats an upload failure as non-fatal, and a half-finished account can be completed by simply retrying signup.
  • Chat message identity. insertMessage returned its own payload instead of the inserted row, so the returned message carried id: undefined — the very field the Realtime channel de-dupes on.

Twelve open items. Severity is from the client's point of view: P0 blocks delivery, P1 blocks a public launch, P2 is quality and polish that should still land inside the window.

Carried over from the audit, worth deciding on

The selfie photo is uploaded and its path stored, but nothing ever reads it back — only the selfieVerified badge is shown. CNIC "verification" is a colour/aspect-ratio heuristic that sets cnic_verified = true automatically; it is honest as a wrong-upload filter but must not be presented to the client as identity verification. Neither is a defect, but both should be stated plainly in the handover.

3. The 15-Day Plan

One developer, five working days a week, 31 August to 18 September 2026. The order is deliberate: the core loop is rebuilt first because every later item — notifications, reporting, entitlements, QA — depends on two real users being able to reach each other.

DayFocusWorkDone when
Phase 1 · Days 1–5 · Make the core loop real
Day 1
Mon 31 Aug		 Matching schema New migration 19_matching.sql: a likes table keyed on (liker_id, target_id, mode), and matches reshaped to a pair row (user_a, user_b, ordered so the pair is unique). RLS: a row is readable by either participant. Backfill/migrate the existing one-sided rows. Add both to the Realtime publication. Two accounts can each see the same match row; a third account cannot.
Day 2
Tue 1 Sep		 Mutual like → match A like_profile(target, mode) RPC that records the like, checks for the reciprocal one, and creates the match atomically, returning whether it matched. Rewire FavoritesContext and the swipe handlers onto it. Fire the match celebration on a real mutual like instead of on every right-swipe. A likes B, B likes A → both see the match and the celebration; A alone sees nothing.
Day 3
Wed 2 Sep		 Two-way chat chat_messages re-keyed to match_id + sender_id; RLS becomes "you are a participant of this match". from_me derived from sender_id at read time. Rewrite matchesService and the Realtime subscription to filter on match membership. Per-side unread counters. A message typed on device A appears on device B within a second, and unread clears per side.
Day 4
Thu 3 Sep		 Chat completeness message_reactions table + long-press reaction picker on MessageBubble (roadmap: "basic emoji reactions"). History pagination so a long thread doesn't load whole. Delivered/ read state. Verify voice notes and image messages survive the new schema. Both sides can react; a 500-message thread opens instantly.
Day 5
Fri 4 Sep		 Move to Rishta — for real Delete the setTimeout simulation. The request becomes a state on the shared match row; the other member sees a pending banner with Accept / Decline; accepting flips the mode for both sides and notifies both. Rishta-mode profile fields gate the request. The signature feature works between two real accounts and is measurable in the data.
Phase 2 · Days 6–9 · Safety, trust and money
Day 6
Mon 7 Sep		 Reporting reports table (reporter, target, reason, context, free text, status) with insert-only RLS for members. Wire the existing ReportDialog in Home and Chat to it. Auto-hide a profile from discovery after N distinct reports. A simple SQL/Studio review view for the client. A report is a row someone can act on, not a toast.
Day 7
Tue 8 Sep		 Block hardening blocked_id becomes the person's uuid, not the match row id. Blocking is enforced in the database: blocked pairs are excluded from discovery both ways, and message insert is refused in either direction. Blocked people disappear from Explore, likes and matches for both sides. After a block, neither member can see or reach the other from any surface.
Day 8
Wed 9 Sep		 Explore+ billing Wire the single V1 paywall to real billing — Play Billing + StoreKit via RevenueCat is the fastest defensible route; a local gateway (JazzCash / Easypaisa) is the alternative if the client prefers PKR rails. Receipt validated server-side in an Edge Function that writes the subscription state. Client decision needed — see Risks. A real purchase on a real device unlocks Explore+; cancelling revokes it.
Day 9
Thu 10 Sep		 Server-side entitlements Move the 15/day like cap into the like_profile RPC so the count cannot be edited by the client. Lock is_explore_plus, subscription_plan and subscription_renews_at against direct user writes (trigger or column-level policy) so only the verified-purchase function may set them. A hand-crafted API call cannot grant itself Explore+ or extra likes.
Phase 3 · Days 10–12 · Reach, real content, compliance
Day 10
Fri 11 Sep		 Push notifications Install expo-notifications, add a push_tokens table, and send from an Edge Function triggered on new match / new message / new like. Every send honours the existing notification_prefs row, which is already built and stored but currently drives nothing. A message to a closed app arrives as a push, and turning the pref off stops it.
Day 11
Mon 14 Sep		 Real content only Put the mock deck behind a dev-only flag so production never shows fabricated members. Replace the hardcoded Explore "Events" with a real table, or hide the tab for V1. Write proper empty states for an early, thin user base — the honest answer to a small deck, rather than filling it with fiction. A production build shows only real people, or an honest empty state.
Day 12
Tue 15 Sep		 Legal & store compliance Real Privacy Policy and Terms covering CNIC collection, photo storage, retention and deletion, hosted and linked in-app. 18+ age gate. Play Data Safety form and App Store privacy labels. Confirm the in-app account deletion path (already built) meets both stores' requirements. Both store review checklists pass on paper.
Phase 4 · Days 13–15 · Harden and hand over
Day 13
Wed 16 Sep		 QA pass 1 Two physical devices, two real accounts, every flow end to end: signup → match → chat → move to rishta → block → report → subscribe → delete account. Add a smoke test suite over the services layer (currently the repo has none). Log and fix. The full journey passes twice with no P0/P1 open.
Day 14
Thu 17 Sep		 Polish & performance Deck pagination instead of fetching every profile, image caching, offline and error states on every network call. Urdu/RTL sweep including the 6 untranslated strings. Accessibility labels. Second QA pass on the fixes. No untranslated string, no unhandled network error, deck scrolls smoothly at 500+ profiles.
Day 15
Fri 18 Sep		 Release & handover Production EAS builds for both platforms, store listings with Urdu and English screenshots, internal testing track. Handover pack: Supabase SQL in order, environment variables, an operations runbook, and a written statement of the known limits (heuristic CNIC check, selfie stored but not displayed). Client holds installable builds, database scripts, credentials and documentation.

4. Risks & Decisions Needed From the Client

ItemWhy it mattersNeeded by
Payment rails Play/App Store billing is mandatory for digital goods on those stores and takes 15–30%. A local gateway (JazzCash / Easypaisa) fits the PKR 999 price point and the Pakistani market far better but is not permitted for in-app digital unlocks on either store. This choice changes Day 8 entirely. Day 6 — before billing work starts
Store accounts Google Play Console and Apple Developer enrolment can take days to clear, and Apple requires a D-U-N-S number for an organisation account. If this is not already in place, Day 15 slips regardless of the code being ready. Day 1 — start immediately
Legal copy The privacy policy and terms need a lawyer's eye because the app stores CNIC numbers and ID photographs. Day 12 assumes copy is supplied or reviewed, not drafted from scratch by the developer. Day 8
Moderation ownership Day 6 creates the reports queue. Someone on the client's side has to actually read it. Without a named owner, the store-required reporting path is a table nobody opens. Day 6
Seed audience Removing the demo deck on Day 11 leaves the app genuinely empty until real members join. A launch plan for the first cohort is needed or the MVP cannot measure adoption — which is its entire purpose. Day 11
Single-developer risk The plan is sized for one developer at full availability with no parallelism. Any sick day, or an App Store review rejection in the final week, consumes the whole buffer. A one-week contingency after Day 15 is realistic. Plan for it now

Definition of done for V1

Two people who have never met can install the app, sign up in Urdu, find each other in the deck, match by liking each other, chat, move that chat to Rishta, and — if either wants out — block or report the other, with the report landing somewhere a human reads. One of them can pay for Explore+ and the other cannot fake it. Both get a push when the other writes. Nothing in the app is a mock. That is the bar Day 15 is measured against.
