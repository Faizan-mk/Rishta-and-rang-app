1. Snapshot

The blocker the previous report was built around is gone. Matches and messages are pair rows that both people can read, the "Move to Rishta" handshake is a real exchange between two accounts, and blocking and reporting are enforced by the database rather than by the client. Ten of the eighteen open items are closed. What is left divides cleanly in two: one feature that was never started (billing), and a set of things that are written but not yet witnessed on two physical devices.

The blocker is cleared

matches now holds one row per pair, (user_a, user_b) stored in ascending order so a pair can only produce one row, readable by either participant. chat_messages is keyed on (match_id, sender_id) and from_me is derived per reader rather than stored. Unread moved to match_reads, one row per person per conversation, so one member reading their copy leaves the other's alone. The setTimeout that answered a Move to Rishta request on the other person's behalf is deleted; the request is a state on the shared row that only the other member may answer.

The distinction this report is organised around

Something can be written, proven in the data, or seen working on a phone. Most of this build is now proven in the data — nineteen assertions across the whole journey pass against the live project (§5). Two things are seen working on a phone: the rishta request and its acceptance. Three things are only written: push arriving on a closed device, live Realtime delivery between two devices, and billing. §5 says exactly which is which, and nothing in this report claims more than that.

7. Known limits and open risks

Stated here so nothing in this report has to be read charitably. The full versions live in docs/handover-notes.md.

  • Push delivery has never been witnessed. push_tokens has never held a real token: Expo Go cannot mint one on SDK 53+, and Android additionally needs FCM credentials on the EAS project. The pipeline is verified as far as Expo's API; a phone receiving a notification is not.
  • Realtime delivery between two devices is unproven. The rows are proven to exist and to be readable by both people; that they arrive within a second is a separate claim that only two open phones can settle.
  • A security grant worth closing. is_blocked_pair is granted to authenticated but was never revoked from public, and a definer function is executable by public unless told otherwise — so anyone holding the anon key can ask whether any two account ids block each other. Confirmed against the live project. It is called from inside RLS policies, so revoking needs a check of which roles those policies serve first. The same pattern was found and fixed on rishta_profile_complete in migration 32.
  • Neither badge is identity verification. The selfie is stored but never reviewed; the CNIC check is a format regex plus a colour/aspect-ratio heuristic. The wording is honest about this now; the review queue that would make it real is Day 12 work.
  • The legal text is not reviewed legal advice. It is drafted to be accurate about what this app actually does, which is not the same thing.
  • No CI. The tests exist and pass; nothing runs them automatically.
  • Migration 32 must be run before the notification behaviour exists. It is applied to the current project; any other environment needs it. All migrations are numbered and re-runnable except 24, which is destructive by design and documented as such.
  • One uncommitted change at the time of writing: the push tap-routing hook and the notification preference verification script.
